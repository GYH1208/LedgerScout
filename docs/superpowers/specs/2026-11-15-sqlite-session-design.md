# SQLite 本地会话持久化设计

日期：2026-11-15（Asia/Shanghai）

## 目标与已确定的选择

用户当前先在本机单人使用 LedgerScout，已选择 SQLite。服务重启后，Web 历史会话、问题、答案、查询状态和证据引用应继续可用，并能在原会话追问。中断查询须由用户显式恢复，启动或刷新页面不得自动调用供应商。

保持现有对话界面、loopback 访问限制、单任务执行、精确金额、日期边界校验、调用预算和检查点恢复语义。

## 方案选择

- JSON 索引：可复用当前文件机制，但会话和任务关联、状态更新需要自行维护一致性。
- **SQLite：用户选定。** 以事务保存本地 Web 元数据，适合单进程、低并发写入，无需独立数据库服务。
- PostgreSQL：可支持后续集中部署，但当前会增加服务配置和维护成本。

以下具体表结构、驱动和迁移方式是实现建议，并非用户逐项指定。用户随后明确要求“直接实现”，已批准本设计范围。实施与验收记录见 `../plans/2026-11-15-sqlite-session-progress.md`。

## 存储边界

默认数据库位于现有输出根目录内：`runtime-results/web.sqlite`，测试使用隔离临时目录。数据库、WAL/SHM 文件、备份以及原始证据都继续被 Git 忽略。

- SQLite 保存会话标题/日期、问题/答案、Web 任务 ID、Runtime 运行 ID、状态、恢复关系、统计用量和证据索引。
- Runtime 文件继续作为原始查询、完整记录、ENS 证明、会话研究上下文和检查点的依据；不把全量转账记录或检查点搬入数据库。
- 结果入库保存脱敏的显示摘要及合法查询引用。证据读取按登记的 session/run/query ID 从 Runtime 结果中取得，继续使用现有字段白名单和每页十条限制。
- 原始金额保留字符串，禁止把 wei、Token 整数或精确小数转为 SQLite REAL/JavaScript Number。
- API Key 和完整配置对象不得入库；问题、标题、答案与错误在写入前沿用现有脱敏逻辑。

建议使用项目要求的 Node >=22.19.0 内置 `node:sqlite`，封装在 web-server 的存储模块中，避免新增原生编译依赖。该 Node 分支中接口仍标为 experimental；只使用已存在的基础 DatabaseSync/预处理语句/事务 API，并在最低支持版本与本机 Node 24 上验证。参考：[Node 22.19 SQLite 文档](https://nodejs.org/download/release/v22.19.0/docs/api/sqlite.html)。

## 数据模型与一致性

1. `sessions`：会话 ID、标题、创建时间、最后活动时间及展示日期。
2. `jobs`：Web 任务 ID、所属会话、会话内顺序、脱敏问题、Web 状态、可空 Runtime runId、resumeOf、脱敏结果摘要/错误及时间戳。
3. `evidence_refs`：Web 任务与该结果引用的 queryId/sourceRunId 的对应关系。历史证据可能属于同一会话的旧运行，不能一律用本轮 runId 拼接查询路径。

使用外键、唯一任务/运行关联、预处理语句、明确状态校验和版本化 schema。会话创建与任务接收在一个事务中提交；只有持久提交后才返回 202 并开始 Runtime。结果摘要、终态和证据引用也在一个事务中更新。写入失败不得回退到内存成功或启动尚未登记的付费调用。

Runtime 的 `onEvent` 增加本轮 runId/sessionId（事件种类与其他字段保持兼容），使 Web 任务尽早持久绑定到正确运行。每轮建立日志后的 `run_started` 回调须在供应商请求之前完成；绑定失败中止本轮。进度仅保留有界的 UI 事件，不把模型上下文或完整工具返回入库。

数据库使用外键校验、WAL 和明确的 busy timeout。schema 升级在事务中执行；遇到未知新版本、损坏或只读数据库时给出安全错误，保留原文件，不静默重建。数据库目录限制为本地用户可读写。数据库操作串行且短小，不在事务中等待网络。

## 重启与中断恢复

数据库与 Runtime 文件无法形成一个跨存储事务，启动时需要协调：

1. 成功占用本地监听端口、取得本服务实例的所有权后才执行启动协调。第二个服务启动失败时不得把第一个服务的任务标成中断。初始化完成前 API 返回明确的未就绪状态；不接收新运行。
2. 已登记任务若有匹配身份、结构与大小限制的 `run-summary.json`，以其持久结果协调数据库，覆盖“Runtime 已结束但数据库未更新”的窗口；重新登记合法证据引用。
3. 数据库仍为 loading 且没有有效终态文件的任务，标为 Web 状态 `interrupted`（页面显示“查询已中断”）。不得伪造 Runtime completed/partial 结果或自动重新执行。
4. 只有登记了 runId、Runtime 检查点及其引用证据通过现有校验、且剩余状态允许恢复时，才展示“恢复本轮查询”。没有检查点的接收中断也保留问题记录，并提示重新发起查询。
5. 恢复仍调用原 `runAgent({sessionId, resumeRunId, input: ''})`，保留原区块、日期、累计预算与证据哈希校验。检查点的 closed/resumedBy 和 Runtime 校验决定实际可恢复性；仅有失败的子任务登记不等于父检查点已经被消费。
6. 恢复请求的登记与单任务占用串行；已被 Runtime 激活的父运行不可重复恢复。所有从磁盘恢复的任务在 API 返回前重新计算恢复可用性。
7. 正常停止时取消在途查询并等待有界收尾后关闭数据库；强制终止则由下次启动协调。关闭数据库后不得再执行异步状态写入。

读本地历史、打开证据和启动协调不会请求 DeepSeek、Alchemy 或 Etherscan。请求边界仍只接受登记 ID，不接受文件路径；从磁盘读取需验证所属会话/运行/查询，限制大小并拒绝逃逸输出根目录的路径或符号链接。

## 历史兼容与容量

首次创建数据库时，对现有 `runtime-results/s_*/r_*` 中结构有效、身份匹配的持久终态记录进行幂等导入，以便此前本地 CLI/Web 查询仍可查看。问题从有界读取的 `run_started` 日志取得，缺失时使用明确的历史运行标题，不根据答案猜测问题。来源不完整或不合法的条目跳过并报告有界数量，原文件保持不变；不自动执行旧任务。

导入只登记合法 ID 和相对引用，历史导入任务 ID 由 Runtime runId 稳定生成。schema 初始化/导入完成标记持久保存；中途失败可重试且不重复导入。不扫描 `web-live_*` 截图验收目录；不导入没有终态的未知旧运行。对目录数、文件大小和单批读取设置边界；超过单批上限时可继续下一批，不能因上限就永久丢弃剩余历史。

以数据库分页读取替代“常驻所有任务”的 Map。移除原本为内存设置的 200 条任务硬上限。当前 `/api/state` 仍只返回最近 30 个会话、各最近 20 轮；超出时页面提示当前展示范围，数据库不删除旧历史。本期不增加搜索、历史翻页、删除、导出或备份按钮。后续可独立补齐较早历史的浏览入口。

## 界面/API 变化

现有布局和正常结果结构保持兼容。新增 Web 中断状态和无完整结果时的恢复入口/说明；区分“已中断”“可显式恢复”“没有可恢复检查点”。继续显示真实失败和 partial，不把历史数据称为最新。

数据库初始化/读写错误在页面给出可行动的本地错误提示，不返回文件路径、Key 或数据库内部异常。历史查询结果的金额、引用、证据分页继续与磁盘一致。启动器继续负责启动本地服务；不引入登录、云同步、后台自动恢复或远程数据库。

## 验收

- 接收/完成后重启本地 API，原会话、问题、答案、精确余额、用量及证据分页一致，仍可继续追问。
- 真实 Pi Runtime 使用离线供应商响应完成查询，重启后复用其历史证据追问；不得出现新增数据 HTTP。
- 子进程在有检查点和无检查点的时刻终止，重启后正确显示中断与恢复可用性，启动本身零供应商请求。
- 显式恢复保留累计预算、固定范围和证据哈希；恢复激活前失败可重试，已经激活则不能重复消费父运行。
- 覆盖终态文件已落盘/数据库尚未更新、数据库写入失败、缺失/损坏证据、第二实例端口占用和旧数据幂等导入。
- 临时目录中的 SQLite 持久化/事务测试、原 HTTP 边界回归、Runtime 回归、类型检查、前端构建与浏览器的重启/证据/中断场景通过。普通测试继续离线；本期不为验证持久化重复产生真实供应商费用。

## 实现者可自行决定

具体 SQL 列名、内部模块拆分、批次大小、准备就绪 API 的内部组织和测试进程控制方式，可在上述语义与边界内决定。保留清晰的存储接口，避免 HTTP/UI 直接散布 SQL；不实现尚未使用的 PostgreSQL 适配层。

备份说明应要求停止本地服务后整体备份输出目录（数据库和证据文件一并保存），不建议在 WAL 写入期间只复制一个 sqlite 文件。
